# 维护这份文档

跨项目的分支、评审、发布和回滚约定见 [标准开发流程](/guide/development-workflow)。本页补充文档仓库的维护要求。

## 写作与更新边界

业务接口和 DTO 在服务仓库维护；本仓库维护跨项目说明、导航及可重复生成的接口索引。生成页面不要手工修改，改动源控制器后重新运行 `npm run api:sync`。

新增服务时维护 `docs/services/catalog.json` 与项目分组 `docs/services/groups.json`；需要纳入控制器索引的后端还应更新 `scripts/api-sources.json`，补齐项目、模块路径、源码默认端口、context-path、网关前缀及说明。生成器的 context-path 配置是显式输入，服务调整前缀后需同步维护。

## 提交前检查

```bash
npm ci
npm test
npm run build
```

构建会检查服务目录与生成索引的结构，以及 VitePress 内部链接。Python 测试覆盖路径组合、数组、注释、HTTP 方法和条件装配识别，不启动业务服务。

## 文档是否已经验证

请区分以下状态，不把静态配置描述成实时状态：

1. 源码声明了路径。
2. 功能在目标环境启用。
3. 已发布正确二进制和路由。
4. 通过鉴权并完成真实业务联调。

注明测试的范围和限制。对于尚未提供 OpenAPI 的服务，先补服务内的规范，不在文档站手写猜测的请求/响应 schema。

## 不提交的内容

生产口令、令牌、私钥、真实用户数据、数据库导出、包含凭据的基础设施账号文档和个人 `.env` 均不进入本项目。示例使用变量或占位符，环境实际值由维护者在对应系统管理。
